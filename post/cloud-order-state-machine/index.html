云资源订单系统：状态机、幂等、重试与补偿如何协作

异步订单不是“发请求后轮询结果”这么简单。它本质上是一条跨服务、跨时间、可能部分成功的状态迁移链。

2026-07-1013 分钟状态机 · 幂等 · 补偿

一、为什么普通 CRUD 思维会失效

创建云主机、网络或存储卷往往要经过参数校验、配额冻结、资源编排、底层创建、关系绑定和结果回写。任何一步都可能超时，而“超时”不代表“失败”：下游可能已经成功，只是响应没有回来。

订单系统最危险的误判，是把调用结果直接等同于业务结果。HTTP 500、超时、连接断开都只能说明本次通信失败，不能证明底层资源没有创建。

二、先设计状态，再写流程代码

状态应表达业务事实，而不是线程运行到了哪一行。一个简化模型可以是：

CREATED
  -> VALIDATING
  -> RESOURCE_CREATING
  -> BINDING
  -> SUCCEEDED

任一可恢复步骤 -> RETRY_WAIT
任一确定失败步骤 -> COMPENSATING -> FAILED
无法自动判断       -> MANUAL_REVIEW

每个迁移都要定义四件事：进入条件、允许来源、执行动作和退出证据。这样状态机才是约束，而不是一组随意赋值的字符串。

三、幂等解决“重复执行会不会产生第二份资源”

调用方重试、消息重复投递、任务恢复都会导致同一步骤执行多次。幂等不能只靠前端按钮置灰，而要落在服务端。

幂等键

为一次业务意图生成稳定的 request_id，在订单表或幂等表建立唯一约束。收到重复请求时，返回原订单，而不是重新创建。

步骤级幂等

订单级幂等只能阻止重复订单，不能阻止同一订单的资源创建步骤重复。调用底层时还需要传递稳定的外部请求号，或在本地记录 order_id + step 的执行结果。

INSERT INTO step_execution(order_id, step, request_id, status)
VALUES (?, 'CREATE_VM', ?, 'RUNNING')
ON DUPLICATE KEY UPDATE request_id = request_id;

四、重试只处理“可能成功”的失败

重试前先分类：

  • 参数错误、配额不足：重试不会改变结果，应立即失败。
  • 网络抖动、服务临时不可用：可以指数退避重试。
  • 调用超时、结果未知：先查询下游事实，再决定是否重试。

重试策略应包含最大次数、退避时间、抖动和熔断。无限重试只会把一次故障放大成持续流量。

五、补偿不是数据库回滚

跨服务流程无法依赖一个本地事务回滚。假设云主机已创建，但网络绑定失败，补偿动作可能是删除主机、释放配额和清理关系。补偿也会失败，因此它本身同样需要状态、幂等和重试。

正向动作补偿动作必须记录的证据
冻结配额释放配额冻结流水号
创建云主机删除云主机底层资源 ID
绑定网络解绑网络绑定关系 ID

六、轮询系统如何避免“越查越忙”

固定频率全量轮询会在任务积压时制造更大压力。更合理的做法是：

  1. 按 next_execute_time 拉取到期任务。
  2. 使用状态和版本号抢占，避免多节点重复执行。
  3. 根据失败次数计算下一次执行时间。
  4. 成功或进入终态后不再参与扫描。
UPDATE orders
SET worker_id = ?, version = version + 1
WHERE id = ? AND status = 'RETRY_WAIT' AND version = ?;

七、可观测性决定系统能否被恢复

至少需要记录订单号、步骤、幂等键、外部资源 ID、状态迁移前后值、失败类型、重试次数和链路 ID。日志应该能回答：“这个资源是谁创建的、执行到哪一步、为什么停住、是否可以安全重放”。

八、最终检查清单

  • 每个状态是否只有明确的合法来源？
  • 重复请求、重复消息和任务重放是否安全？
  • 超时后是否先查事实，而不是直接再创建？
  • 补偿失败是否能继续恢复或转人工？
  • 是否能从订单追踪到底层资源和每次状态迁移？
