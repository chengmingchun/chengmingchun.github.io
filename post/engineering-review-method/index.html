工程复盘

如何写一份真正有用的工程复盘

复盘的目标不是证明谁犯了错，而是让下一次相似故障更难发生、更快发现、更容易恢复。

2026-07-1010 分钟故障 · 可观测性 · 改进闭环

一、只有时间线，不算完整复盘

“10:02 告警、10:10 定位、10:30 恢复”只能说明发生了什么，不能解释系统为什么允许它发生。真正有价值的复盘要从时间线中抽取控制缺口：哪条防线没有建立，哪条防线失效，又为什么没有更早发现。

二、先分开事实、判断和假设

类型示例
事实数据库连接池在 10:03 达到上限 200
判断请求堆积由慢 SQL 导致
假设发布前数据量较小，所以压测没有暴露问题

事实应能被日志、指标、配置或提交记录验证；判断需要证据链；假设必须在复盘后通过实验确认，不能直接写成结论。

三、用五层问题替代“人为失误”

  1. 触发条件：什么变化让故障开始？
  2. 缺陷机制：代码、配置或数据如何把触发放大？
  3. 保护失效：限流、超时、隔离、回滚为什么没有阻断？
  4. 发现延迟：为什么用户先于监控发现？
  5. 恢复阻力：为什么定位或恢复花了这么久？
“工程师配置错误”不是根因。系统为什么允许一个高风险配置未经校验进入生产，才是值得改进的问题。

四、影响评估要从用户视角表达

不要只写 CPU 90%、错误率 12%。还要描述影响了哪些用户、哪些功能、持续多久、是否造成数据错误或重复执行，以及是否存在后续补偿成本。

五、根因通常不止一个

可以把原因分成四层：

  • 直接原因：触发故障的具体代码或配置。
  • 促成因素：数据增长、依赖抖动、容量不足等放大条件。
  • 检测缺口：缺少哪些指标、告警或演练。
  • 组织缺口：评审、发布、所有权和知识传递是否存在问题。

六、改进项必须能验收

“加强监控”“提高稳定性”无法关闭。一个合格的行动项应包含负责人、截止时间、验收条件和失败后的升级路径。

行动项：为订单轮询积压增加分级告警
负责人：订单服务 Owner
截止时间：2026-07-17
验收：积压超过 5,000 持续 5 分钟触发告警；演练环境验证通知链路
状态：OPEN

七、按防线组织行动项

防线目标例子
预防让缺陷难以进入生产静态校验、评审清单、容量基线
发现更早知道系统偏离业务指标、SLO、异常趋势告警
缓解限制故障影响范围限流、熔断、隔离、降级
恢复缩短恢复时间一键回滚、Runbook、数据修复工具

八、复盘会议如何避免变成辩解会

  • 会前共享事实材料，把会议时间用于讨论机制和改进。
  • 主持人阻止人身归因，持续追问系统为何没有防住。
  • 争议结论标记为待验证假设，安排实验而不是现场争论。
  • 会议结束前确认行动项的负责人和验收标准。

九、复盘完成不等于问题关闭

行动项完成后还要回看：新监控是否真实触发过、演练是否能在目标时间恢复、类似故障是否在其他服务存在。高质量复盘最终会沉淀为平台能力、默认配置、自动检查和组织标准，而不是留在文档里。

十、一页复盘模板

  1. 摘要与用户影响
  2. 关键时间线
  3. 事实证据
  4. 直接原因与促成因素
  5. 保护、发现和恢复缺口
  6. 做得好的地方
  7. 可验收行动项
  8. 后续验证日期
