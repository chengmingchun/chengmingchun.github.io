缓存一致性不是一道八股题：从读写竞态到工程兜底

不存在脱离业务的一套“标准答案”。先识别会出现什么竞态，再决定需要多强的一致性和多高的实现成本。

2026-07-1012 分钟Redis · 一致性 · 并发

一、缓存一致性到底在保护什么

数据库是真实来源，缓存是派生副本。所谓一致性问题，本质是派生副本在一段时间内与真实来源不同。工程上需要回答的不是“能否绝对一致”，而是：

  • 旧数据最多允许存在多久？
  • 哪些字段读旧值会造成资金、权限或库存风险？
  • 读流量、写流量和热点程度如何？
  • 是否接受短暂回源或缓存不可用？

二、推荐基线：更新数据库，提交后删除缓存

begin transaction
update database
commit

delete cache

相比“更新数据库后更新缓存”，删除缓存更简单：下一次读取会从数据库获得新值并回填，避免在写路径中重复实现对象组装逻辑。

删除必须发生在数据库事务提交之后。否则缓存被删后，另一个读请求可能读到尚未提交的旧数据库值，并把它重新写回缓存。

三、最经典的旧值回填竞态

  1. 读请求 A 缓存未命中，开始查询数据库，读到旧值 V1。
  2. 写请求 B 更新数据库为 V2，并删除缓存。
  3. A 查询完成，把 V1 回填到缓存。

最终数据库是 V2，缓存却重新变成 V1。这个窗口并不常见，但在慢查询、热点键或写流量升高时可能被放大。

四、不同兜底方案的边界

TTL：限制错误持续时间

TTL 不是一致性方案，却是所有方案都应该具备的最后保险。它保证错误缓存不会永久存在。重要数据使用较短 TTL，稳定且构建昂贵的数据使用较长 TTL，并增加随机抖动避免集中失效。

延迟双删：压缩旧值回填窗口

update database
commit
delete cache
sleep(short delay)
delete cache again

第二次删除试图清理并发读请求回填的旧值。缺点是延迟难以准确估计，睡眠会占用执行资源，而且第二次删除仍可能失败。因此它更适合作为过渡性增强，而不是最终保证。

删除失败重试：保护写后失效

数据库更新成功但缓存删除失败时，旧值会持续到 TTL 到期。可以把删除事件写入本地消息表，与业务事务一起提交，再由异步任务可靠重试。

订阅 binlog：把缓存失效从业务代码解耦

通过 CDC 订阅数据库变更并删除缓存，可覆盖绕过应用服务的写入。但系统会引入消费延迟、顺序、重复事件和运维复杂度，依然需要幂等和监控。

五、热点回填还要解决击穿

缓存失效后，大量请求同时查数据库并回填，会形成缓存击穿。常见做法有互斥锁、逻辑过期和请求合并：

value = cache.get(key)
if value exists: return value

if lock.tryAcquire(key):
    value = database.query(key)
    cache.set(key, value, ttl)
    lock.release(key)
    return value

wait briefly and retry cache

锁的粒度应落在具体缓存键，并设置超时，避免构建线程异常后形成永久阻塞。

六、主从延迟会让“正确删除”也回填旧值

如果写入主库后删除缓存，而回源查询走从库，从库可能尚未追上主库，读请求仍会拿到旧值并回填。关键写后读可临时走主库、等待 GTID，或在请求上下文中维持一段读主窗口。

七、按业务等级选择方案

场景建议
展示型数据提交后删缓存 + 合理 TTL
高并发热点基线方案 + 请求合并/逻辑过期
权限、库存等敏感数据关键读取回源或版本校验，缩短缓存窗口
多写入口CDC/binlog 失效 + 可靠消费

八、验收清单

  • 缓存删除失败是否有指标、重试和死信处理？
  • TTL 是否带随机抖动？
  • 热点键失效时数据库能否承受回源峰值？
  • 主从延迟期间关键读是否会回填旧值？
  • 能否通过版本号或更新时间识别缓存是否落后？
