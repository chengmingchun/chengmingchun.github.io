Agentic 研发系统如何收敛：任务图、证据链与质量门禁

多 Agent 的价值不在于模拟多少角色，而在于让复杂任务被拆解、执行、验证并在失败时回退到正确节点。

2026-07-1015 分钟Agent · MCP · 工作流

一、为什么“让几个 Agent 互相讨论”很难上线

自由对话看起来很智能，却缺少三个工程属性：任务何时完成、结果如何验收、失败后从哪里恢复。只要这三个问题没有结构化答案，系统就容易无限循环、重复调用工具或产生无法追责的最终文本。

Agent 系统的核心抽象不是角色，而是带输入、输出、前置条件和验收规则的任务节点。

二、把流程建模成有向任务图

以“从需求生成可合并代码”为例，可以拆成：

需求澄清
  -> 仓库检索
  -> 方案设计
  -> 代码修改
  -> 静态检查
  -> 测试执行
  -> 差异审查
  -> 交付摘要

每个节点都应声明：

  • 输入：它依赖哪些结构化事实。
  • 产物：必须输出文件、补丁、测试报告还是决策记录。
  • 工具权限：可以读什么、写什么、是否能执行命令。
  • 通过条件：谁验证、验证规则是什么。
  • 失败去向：重试当前节点、回退上游还是转人工。

三、证据链比“模型说完成了”更重要

每个结论都应绑定可检查证据。例如：

声明证据
代码已经修改提交 SHA、文件 diff
测试通过命令、退出码、报告路径
接口兼容契约测试或前后版本对比
性能改善同环境基准数据

没有证据的“已完成”只能算模型判断，不能进入自动发布链路。

四、Planner、Executor、Reviewer 应如何分工

Planner：约束问题空间

负责拆解任务、识别依赖、安排执行顺序和设定验收标准。Planner 不应直接写大量代码，否则计划与执行耦合后难以审查。

Executor：在有限权限内产生产物

执行节点只拿到完成当前任务所需的上下文和工具。修改文件时应限制路径，调用外部系统时使用最小权限，并把操作结果结构化返回。

Reviewer：验证，而不是重新生成

Reviewer 应优先读取 diff、测试报告和约束清单，指出具体失败项。若 Reviewer 只是再问一次大模型“看起来对吗”，它无法形成真正的质量门禁。

五、MCP 与 Skill 的边界

MCP 服务更适合提供标准化外部能力，例如仓库检索、数据库查询、工单系统和部署平台。它解决“Agent 如何安全访问能力”。

Skill更适合封装稳定的方法和流程，例如 SQL 排障步骤、代码审查清单或故障复盘模板。它解决“Agent 应该按照什么方法做事”。

工具返回原始事实，Skill 组织推理过程，两者不要混成一个巨大的黑盒提示词。

六、如何防止无限循环和成本失控

  • 为任务图设置最大节点数、单节点最大重试和总 token/时间预算。
  • 同一工具相同参数连续失败时，不允许无条件再次调用。
  • 每次重试必须携带新的证据或修改后的参数。
  • 把“缺少信息”作为合法终态，允许向用户请求关键输入。
  • 高风险写操作必须经过显式批准或策略引擎。
if attempts >= max_attempts:
    return NEED_HUMAN
if repeated_tool_call_without_new_evidence:
    return BLOCKED
if quality_gate.failed:
    return rollback_to(quality_gate.owner_node)

七、质量门禁应该检查什么

门禁应按产物类型设计，而不是所有任务共用一个评分：

  • 代码：编译、静态扫描、单测、契约测试、diff 范围。
  • 架构方案：需求覆盖、关键约束、替代方案、风险与回滚。
  • 需求文档：歧义、验收条件、异常流程和角色权限。
  • 发布动作：变更窗口、审批、监控、灰度和回滚脚本。

八、可运营性：上线后如何持续改进

记录每个节点的输入摘要、模型版本、工具调用、耗时、token、失败原因和人工接管点。真正有价值的指标不是“调用了多少次模型”，而是任务成功率、一次通过率、人工介入率、平均恢复成本和错误逃逸率。

九、最小可行架构

  1. 先选一个边界清晰、可自动验收的场景。
  2. 用确定性的工作流承载主流程，只在需要判断的节点调用模型。
  3. 每个节点输出结构化 JSON 和证据引用。
  4. 先建立测试与门禁，再增加 Agent 数量。
  5. 把人工接管设计成正常路径，而不是异常兜底。

能稳定收敛的单 Agent 工作流，通常比无法验收的多 Agent 群聊更接近生产价值。
